# Intero Golden Case

[English](GOLDEN_CASE.md) · 简体中文

## 目的

这是 Intero 的权威端到端产品场景。产品设计、Agent 行为、领域契约、浏览器验收和 Provider Canary 都应该讲述同一个故事。它不表示所有团队都这样工作，而是第一组可以重复运行的案例，用来检验产品主张是否成立。

分阶段实现方式与证据门槛见
[Golden Case 交付计划](plans/2026-08-01-001-golden-case-delivery-plan.md)。

这个案例必须证明：团队可以在包含多个 Project 的 Team Room 中自然聊天，只需要提及 `@Intero`，就能解决一个真实的跨项目冲突，而不必手动路由上下文，也不会暴露私有 Agent 活动。

## 被测试的产品模型

| 角色                  | 代表谁 | 职责                                                                     |
| --------------------- | ------ | ------------------------------------------------------------------------ |
| 个人替身              | “我”   | 保护私人上下文、帮助一个人，只共享经过授权的工作状态                     |
| 共享 Room 中的 Intero | “我们” | 理解经过授权的对话、判断作用域、协调共享工作，维护经过人类确认的项目现实 |
| 外部 Coding Agent     | 执行   | 在授权范围内实现、检查和验证工作                                         |

Project 是内部状态、授权和证据作用域，不是用户需要记住并分别提及的机器人。共享空间中可见的 Agent 始终叫 `Intero`。

## 已确定的产品决策

1. 用户在 Team Room 中只需要提及 `@Intero`。
2. Intero 自行判断讨论属于一个 Project、多个 Project、Team 层面，还是暂时无法确定。
3. 作用域推断只能路由信息，不能授予权限或扩大可见范围。
4. 经过授权的对话可以表达意图、观察、分歧或候选决定，但它本身不是实现事实。
5. 个人替身共享有边界的语义 Work State，不共享原始提示词、文件、Diff、终端输出或私人对话。
6. 兼容的工作保持安静。有充分证据、置信度高的冲突可以自动创建一个可撤销的临时讨论。
7. Intero 在被询问或确实存在值得关注的协调问题时，可以作为群机器人发言，但不能形成持续的状态消息流。
8. 面向人的内容先使用普通语言，再按需展示准确的技术证据。
9. 优先级、负责人、批准、时间安排、外部承诺和最终决定必须由人确认。
10. 重复信号更新同一条协调路径，不能创建新的 Thread、Room 消息、提示或 Inbox 项。

## 测试场景

### 共享空间

- Team：`Intero Lab`
- Team Room：`#engineering`
- 同一个 Room 中讨论的 Project：
  - `Auth Platform`
  - `Mobile App`

### 人与 Agent

- Alex 主要负责 `Auth Platform`。
- Priya 主要负责 `Mobile App`。
- Alex 和 Priya 各自拥有一个私有的个人替身。
- 每个人都绑定了经过授权的 Coding Agent。
- `Intero` 是 `#engineering` 中唯一可见的共享 Agent 身份。

### 可共享的工作状态

Alex 的 Coding Agent 通过 Alex 的个人替身上报：

- Project：`Auth Platform`
- 意图：把 `retryDelayMs` 改名为 `retryAfterMs`，并删除旧字段
- 共享边界：公共重试配置契约
- 计划删除时间：2026-08-08
- 验证：Auth 侧单元测试通过

Priya 的 Coding Agent 通过 Priya 的个人替身上报：

- Project：`Mobile App`
- 意图：完成客户端重试处理
- 依赖：客户端仍然读取 `retryDelayMs`
- 共享边界：同一个公共重试配置契约
- 验证：向 `retryAfterMs` 的迁移尚未完成

这些可共享记录都不包含原始提示词、源文件、Diff、终端日志或无关的私人 Work State。案例开始前，不预置 Coordination Thread、Room 摘要或 Action Inbox 项。

## Golden Path 主流程

### 1. Team Room 中的自然对话

Alex 在 `#engineering` 中发送：

> @Intero，现在可以删除 `retryDelayMs` 了吗？

Alex 不需要选择 Project Agent、填写表单，也不需要关联一个事先存在的 Feature、Spec 或 Work Item。

### 2. Intero 判断作用域

Intero 将这条消息和两条可共享的边界 Claim 关联起来，判断这个问题同时涉及 `Auth Platform` 和 `Mobile App`。

界面显示可纠正的作用域：

> `Auth Platform` + `Mobile App` · 跨项目

Intero 不会因为完成了这次推断，就获得任何额外的私人上下文访问权限。

### 3. Intero 只发言一次并打开协调

由于冲突明确、仍然有效、来自不同人员，并且有共享 Claim 支持，Intero 创建或复用唯一一个临时讨论，并在 Room 中发送一条简短内容：

> **现在删除 `retryDelayMs` 可能导致移动端重试失效。**
>
> Auth Platform 计划删除这个字段，但 Mobile App 仍然依赖它。两个项目需要确认一段兼容时间。
>
> [打开讨论] [为什么关联这两个项目？] [关联错误]

第一层内容必须直接说明：

- 发生了什么；
- 为什么重要；
- 涉及哪些 Project；
- 需要解决什么问题。

用户不需要理解内部的 Claim 匹配概念，才能看懂这段说明。

### 4. Intero 路由相关性，但不制造行动

Priya 正在查看 `#engineering` 时，原有 Room 内容旁显示一条本地、可忽略的提示：

> 这可能影响你正在进行的移动端重试工作，要进去看一下吗？

被动相关性不会创建 Action Inbox 项、新的 Room 消息、未读数或普通通知。Priya 可以打开、忽略、静音或之后重新查看这个讨论。

### 5. 临时讨论已经准备好上下文

临时讨论顶部按照三个层次展示内容。

**几秒内看懂**

- 发生的变化：Auth Platform 计划删除 `retryDelayMs`。
- 影响：Mobile App 仍然读取它，移动端重试可能失效。
- 待解决问题：旧字段需要继续兼容多久？
- 当前行动：Alex 和 Priya 需要确认兼容时间。

**解决问题**

- 方案 A：同时保留两个字段到 2026-08-08，等待 Mobile App 完成迁移。
- 方案 B：在 Mobile App 提供新的验证证据之前，推迟删除旧字段。
- 在人确认之前，任何方案都不能被写成已经作出的决定。

**核对证据**

- 准确的共享边界和字段名称；
- 来源 Project、人员、个人替身、Coding Agent 绑定和 Work State；
- 观察时间、新鲜度和修订；
- 当前测试和迁移证据；
- 用不同陈述类型展示事实、Intero 解释、建议和尚未解决的不确定性。

### 6. 人作出会产生实际后果的决定

Alex 和 Priya 选择方案 A，并明确作出承诺：

- Priya 在 2026-08-07 前完成 Mobile App 迁移并提供重试验证。
- Alex 保持 `retryDelayMs` 兼容，直到验证证据可用，并且不早于 2026-08-08 删除旧字段。

Intero 准备结论草稿，但不会自己发明负责人和日期。如果仍然缺少必要确认，它只为相关负责人创建或更新一个去重后的 Action Inbox 项：

> 确认 `retryDelayMs` 的兼容时间。

在记录必要的人类确认之前，临时讨论保持打开。

### 7. Intero 完成闭环

确认后，Intero：

1. 使用经过确认的决定、行动、由人选择的负责人、日期、来源和剩余不确定性关闭临时讨论；
2. 在原位置更新 `#engineering` 中的同一条内容；
3. 保存带有来源信息的 Decision 和受影响工作上下文；
4. 只把有边界、经过确认的结果发送给相关个人替身和 Coding Agent；
5. 在重试和重放时继续复用同一个 Thread、Room 消息、相关性记录和 Inbox 项。

最终的 Room 内容是：

> **兼容时间已经确认。**
>
> `retryDelayMs` 保持支持到 2026-08-08。Priya 将在 2026-08-07 前验证 Mobile App 迁移；Alex 只会在证据可用之后删除旧字段。
>
> [查看决定与证据]

摘要修订不会创建新的 Room 消息、未读数或普通通知。

## 必须通过的对照分支

### A. 兼容对照保持安静

Auth Platform 新增 `retryAfterMs`，但明确继续保留 `retryDelayMs`。Mobile App 继续使用旧字段。两边的共享 Claim 彼此兼容。

预期结果：

- Intero 不主动发消息；
- 不创建 Coordination Thread；
- 不显示相关性提示；
- 不创建 Action Inbox 项；
- 不产生冲突状态。

如果有人明确 `@Intero` 提问，Intero 可以用普通语言回答，但仍然不能创建协调工作。

### B. 作用域模糊时只询问一次

有人发送：

> @Intero，重试逻辑好像有问题。

多个 Project 都包含重试逻辑，当前证据不足以安全选择一个作用域。

预期结果：

> 你指的是哪个上下文？
>
> [Auth Platform] [Mobile App] [跨项目] [暂时不属于具体项目]

在获得澄清之前，Intero 不创建 Bug、Thread、Inbox 项或权威 Project 关联。

### C. 纠正会更新同一条路径

Priya 表示 Mobile App 已经完成迁移，之前的 Work State 已经过期。Intero 保存这次纠正，请求或读取经过授权的当前证据，并更新同一个 Room 内容和 Thread。

如果新证据消除了冲突，Intero 使用可见的原因关闭或驳回协调路径，不留下错误决定、重复消息或重复行动。

### D. 受限上下文不能泄露

Intero 发现可能与当前查看者无权访问的 Project 有关。

预期结果：

- 不暴露受限 Project 的名称、消息、工作细节、参与者或证据；
- 当前 Room 最多只能收到符合策略的最少说明；
- 可以向有权限的人发送有边界的评审请求，但不能反向泄露当前 Room 的私有内容；
- 作用域推断永远不能转化为权限。

### E. 重放保持幂等

同一条消息、Work State、Worker 任务、实时事件或确认被重复发送三次。

预期结果：

- 只有一个活动 Coordination Thread；
- 只有一条来源 Room 摘要；
- 最多只有一个仍未解决的相关 Action Inbox 项；
- 每个人只有一个当前相关性状态；
- 只有一个经过人类确认的结论。

### F. 满足条件、尚未被询问的冲突可以主动发言一次

同一个来自不同人员、有明确共享边界的冲突，在任何人提及 `@Intero` 之前已经成为可共享状态。

预期结果：

- Intero 可以主动创建同一条简短 Room 内容和边界明确的临时讨论；
- 这条内容解释为什么现在值得占用人的注意力；
- 重复评估只更新原内容，不会再次发消息；
- 置信度较低的解释保持安静，或只在当前上下文中询问，而不是宣布冲突。

## 验收矩阵

| 维度         | 必须提供的证据                                                                        |
| ------------ | ------------------------------------------------------------------------------------- |
| Agent 模型   | 用户只提及 `@Intero`；个人替身没有授权时不会公开发言                                  |
| 作用域路由   | 单 Project、跨 Project、Team 层面和模糊情况可以区分并纠正                             |
| 冲突检测     | 冲突指出正确的共享边界、来源、Project 和受影响人员                                    |
| 低噪音       | 兼容对照产生零条主动协调内容                                                          |
| 群机器人行为 | Intero 被提及时回答；满足条件、尚未被询问的冲突最多产生一条主动 Room 内容             |
| 理解成本     | 用户可以从简短内容中解释发生了什么、为什么重要、自己是否要处理，不需要别人翻译        |
| 技术证据     | 可以核对准确技术标识和当前来源，同时不会压垮第一层内容                                |
| 人类权限     | Intero 不会发明优先级、负责人、日期、批准或承诺                                       |
| 注意力路由   | 被动相关性不进入 Action Inbox；必要确认只创建一个去重后的项目                         |
| 隐私         | 原始或未授权的个人、Agent、Room 或 Project 上下文不会跨越可见性边界                   |
| 状态一致性   | Room、Thread、Inbox、Decision、Work State、个人替身和 Coding Agent 获得同一个兼容结果 |
| 恢复能力     | 纠正、重试、重放、忽略和关闭不会产生重复或矛盾状态                                    |

## 测试顺序

1. **确定性领域测试：** Claim 规范化、作用域候选、兼容对照、满足条件的冲突、过期和纠正后的证据。
2. **持久化与 API 测试：** 授权、来源、去重、原位摘要修订、上下文相关性、确认和关闭。
3. **浏览器验收：** 分别以 Alex 和 Priya 运行完整 Team Room 流程，验证准确可见状态和没有产生的噪音。
4. **真实 Provider Canary：** 通过实际配置的 Provider 生成人能看懂的解释与摘要；确定性证据仍然是冲突成立的原因。
5. **目标环境 Canary：** 在本地 Fixture 之外证明持久 Worker、实时交付、重试行为和发布链路。

## 不属于这个 Golden Case 的内容

- 为每个 Project 暴露一个独立 Agent；
- 自动决定优先级、人员安排、时间、批准或发布；
- 完整重建 Product Capability 或 Capability Health；
- 替代所有外部聊天、项目管理、Git、CI 或测试系统；
- 证明这套工作流适用于所有团队或交付阶段。

## 成功定义

当 Alex 和 Priya 能够在一个包含多个 Project 的 Team Room 中自然聊天，依靠唯一可见的 Intero 发现并讲清楚跨项目冲突，由人亲自作出会产生实际后果的决定，然后回到工作中，并且所有经过授权的产品界面都携带同一个结果；同时，兼容对照保持安静，这个 Golden Case 才算成功。
