# Intero 产品路线图

[English](PRODUCT_ROADMAP.md) · 简体中文

## 目的

Intero 不预先承诺一套普适的 AI 原生软件工程方法。团队结构、协调成本和有效流程，可能在探索、快速交付、稳定化和维护阶段表现得完全不同。这些差异本身就是需要研究的问题，而不是产品可以暗中预设的答案。

因此，路线图以证据门槛推进，而不是以功能数量或固定日历推进。每个阶段都必须先证明一个范围更窄的判断，Intero 才扩大产品界面或 Agent 权限。

## 产品主张

Intero 首先是面向软件团队的协作感知层。在这样的团队中，人与 Coding Agent 正在以越来越高的自主性工作：

> 在不监控私人活动、不把每一个 Agent 动作都变成打扰的前提下，帮助团队及时发现哪些独立工作需要共同理解、协调或重新验证。

这个主张可以跨越不同工作阶段。阶段之间变化的是信号、风险阈值和所需证据，而不是团队维持可信共享现实的需要。

更长期的目标，是探索一个 AI 原生的软件工程与项目管理承载平台：项目现实从经过授权的对话、实际工作、决定和证据中形成。自动协调是第一阶段的切入口；如果证据支持，它也会成为更大平台的底层引擎。路线图不会预先假设所有传统项目管理对象和工作流都必须属于 Intero。

## 产品结构

### 核心产品

以下能力必须成为可信而连贯的整体：

- 把经过授权的对话作为人的意图、问题、分歧和候选决定的一类核心来源，但不把讨论直接当成事实；
- 有隐私边界的 Agent Work State 和明确共享的 Claims；
- 在条件允许时关联仓库、测试、CI 和运行时证据；
- 作为环境感知而非任务排序的 Team Pulse；
- 可解释的冲突、依赖和相关性检测；
- 边界明确的 Coordination Thread；
- 只承载具体人类决策与承诺的 Action Inbox；
- 默认讲人话、同时允许按需核对准确技术证据的协调说明；
- 来源、授权、纠正、去重和恢复机制。

### Agent 角色与作用域路由

产品面向用户提供两种 Intero Agent 角色：

- 个人替身代表一个人，并保护他的私人上下文；
- 共享 Room 中的 Intero 代表这个共享空间，并维护经过授权、人类确认的团队现实。

外部 Coding Agent 负责执行。Project 是 Intero 背后的状态、策略和证据作用域，而不是用户需要分别提及的 Project Agent。一个 Team Room 可以同时讨论多个项目；用户只需要 `@Intero`。Intero 根据对话、关联工作、参与者和可共享 Work State，判断它属于单个 Project、跨 Project、Team 层面，还是暂时无法确定。作用域推断只能路由信息，不能授予访问权限或扩大可见范围。证据含糊时，Intero 应该只请求一次轻量澄清，而不是静默选择某个 Project。

### 兼容上下文

Project、Epic、Feature、Work Item、Sprint、Spec Review、代码引用和未来的外部系统集成，可以帮助 Intero 理解已经声明的工作。它们是有用的上下文，但不是产品主张；在第一阶段证明自动协调时，Intero 不需要拥有团队的每一个权威系统。后续证据可能支持其中一些对象成为更大平台的一部分，但这不是验证初始切入口的前提。

### 研究支线

以下方向仍然是可以被证伪的假设：

- 发现 Agent 没有明确声明的语义关系；
- 随工作阶段或风险变化的协调阈值；
- Product Capability 重建和 Capability Health；
- 更广泛的 AI 原生团队软件工程模型。

只读研究可以并行进行。但在达到各自的证据门槛之前，这些方向不应获得新的领域对象、数据库迁移、自动修改能力或顶级产品页面。

## 交互模型

Intero 应该逐级使用人的注意力：

```text
环境感知
→ 上下文相关性
→ 明确的人类行动
→ 人类确认的后果
```

| 层级           | 产品行为                                                 |
| -------------- | -------------------------------------------------------- |
| 环境感知       | Team Pulse 和静默刷新的摘要；不做日常打扰                |
| 上下文相关性   | 相关人员正在查看上下文时，显示可解释、可忽略的小提示     |
| 明确的人类行动 | 只有决策、评审或承诺才创建一个去重后的 Action Inbox 项   |
| 人类确认的后果 | 需要预览、授权、审计、幂等，并且可以撤销的修改或关闭操作 |

“可能相关”不等于“需要行动”。模型置信度也不等于打扰某个人的权限。

面向人的协调信息也应该逐级展开：

```text
发生了什么、为什么重要、我是否需要处理
→ 哪些工作发生冲突、问题还剩什么、有哪些选择
→ 准确标识、来源、证据、新鲜度和不确定性
```

第一层必须使用普通语言。准确的 API、字段、模块、测试和修订名称仍然作为技术锚点保留。已确认事实、模型解释、建议和人类确认的决定不能被写成同一种陈述。

## 以证据推进的路线图

这里的 `R` 代表研究和交付门槛，而不是版本发布日期承诺。

### R0 — 可信的产品基线

在增加新的大型产品界面之前，先完成现有产品闭环工作和目标基础设施上的发布验证。

截至 2026-08-01：仓库内实现和可重复的本地生产级验证已经完成；最终托管环境的
Canary 仍是 R0 的退出阻塞项。证据见
[R0 发布验证记录](validation/R0_RELEASE_GATE_2026-08-01.md)。

退出证据：

- Agent、Work State、实时状态、Action Inbox 和授权主链路可恢复、可观测；
- 发布基线保持绿色；
- 在目标环境中完成生产级容量、故障切换和 Canary 验证；
- 隐私或人类权限失败始终是硬阻塞。

### R1 — 证明协调内核

实现状态（2026-07-31）：显式共享 Claim 合约、确定性匹配器、多来源持久化、MCP
对照评估和 canonical 冲突物化均已实现并完成本地验证。在将该门槛标记为“已证明”之前，
仍需补齐浏览器验收、部署后的持久化 Worker Canary 和目标环境发布证据。

让一组严格对照案例通过真实、经过授权的 Work State：

1. 一个兼容的跨边界修改保持安静；
2. 对同一个共享边界持有不兼容假设时，只创建一个边界明确的 Coordination Thread。

第一版应该优先使用明确、结构化、可共享的边界 Claims，并进行确定性匹配。模型可以解释候选冲突，但不能成为产品宣布冲突的唯一依据。

退出证据：

- 控制案例不创建 Thread、提示或 Inbox 项；
- 冲突案例识别出正确的共享边界、来源和人员；
- 重放不会产生重复 Signal 或 Thread；
- 不暴露原始提示词、文件、Diff、终端输出或私人 Work State；
- 链路来自真实 MCP 和 Worker，而不是预置的 Coordination 数据。

### R2 — 证明低噪音协作

实现状态（2026-07-31）：canonical 子 Thread、Room 中唯一且原位更新的摘要、
上下文相关性的忽略/静音/重新关注、仅确认时进入 Action Inbox，以及专用幂等关闭路径，
均已实现并完成本地验证。用户可见的浏览器评估和真实 Provider Canary 仍是待补证据。

把检测到的冲突变成完整交互：

- 在来源 Room 中显示一个临时讨论入口；
- 在原位置静默更新简短摘要；
- 用普通语言解释冲突、影响和待解决问题，同时允许按需展开准确的技术证据；
- 只在相关人员查看上下文时显示可解释提示；
- 只有确实需要决定或确认时才进入 Action Inbox；
- 在同一个 Room 入口中回显人类确认的结构化结论。

退出证据：

- 摘要刷新不增加消息、未读数或普通通知；
- 被动相关性不创建 Action Inbox 项；
- 相关人员无需额外口头解释即可解决冲突；
- 相关人员可以从简短说明中理解发生了什么、为什么重要、自己是否需要处理，而不必解码系统内部概念；
- 展开后的内容保留准确边界、来源、不确定性和人类确认的结果；
- Room、Coordination Thread、Inbox 和相关工作状态之间没有矛盾；
- 纠正、忽略、重试和重放都保持安全。

### R3 — 跨工作阶段试点

先使用研究标签，而不是实现新的“工作模式引擎”，比较：

- 探索；
- 快速交付；
- 稳定化；
- 维护。

观察相关信号、可接受的不确定性和介入阈值，是否会随着可逆性、影响范围、产品成熟度和运行风险而变化。

退出证据：

- 有价值的协调能力在多个真实事件中重复出现；并且
- Intero 要么在不止一个工作阶段证明价值，要么主动收窄到价值真实存在的阶段和团队类型。

### R4 — 只读 Capability Health 实验

收集团队内部真实事件、进行外部问题调研，并从经过授权的对话、工作和验证证据中重建 Product Capability 候选。对话可以表达意图或观察到的结果，但不能证明某项能力确实可用。每个候选都必须允许人接受、纠正、合并、拆分或拒绝。在证明有效之前，健康状态投影保持静默，不能自动创建协调工作。

退出证据：

- Capability Health 提供了 Feature Tracker、Work State、测试或现有项目系统没有表达的信息；
- Capability 粒度和纠正成本可以接受；
- `supported`、`at_risk` 和 `regressed` 都能由当前证据解释；
- 兼容的控制案例保持安静，而矛盾证据只创建一条有效协调路径。

### R5 — 决定产品边界

根据累积证据决定 Intero 应该：

- 主要保留为冲突与注意力协调层；
- 继续实现 AI 原生项目管理与产品共享现实平台的长期目标；
- 让 Capability Health 保持只读辅助能力；
- 通过集成获取更多项目管理上下文，而不是自己拥有；
- 收窄到特定类型的 AI 密集型团队；或者
- 停止没有通过验证的假设。

收窄或否定一个方向也是有效结果。

## 衡量方式

Intero 不应该优化摘要、Thread、任务或通知的数量。应该衡量：

- 有效冲突的准确率，以及通过抽样发现的漏检率；
- 每人收到的错误提示和 Inbox 打扰；
- 从冲突状态出现到被发现、确认和关闭的时间；
- 用户是否仍然需要在产品外解释到底发生了什么；
- 用户能否从简短说明中理解事件、影响、相关性和所需行动，而不需要别人再次翻译；
- 减少了多少人工状态汇报、上下文搬运、跟进和项目记录维护；
- 是否在集成或发布前发现回归和不兼容修改；
- 人类纠正和忽略 AI 判断的比例；
- 必须为零的隐私、授权和不可逆越权事件。

长期结果是：

> 在保留团队自主性和交付速度的同时，减少团队共享现实悄然分叉的次数。

## 明确不做什么

当前路线图不承诺 Intero 成为：

- 分配和批准所有工作的中央 AI 管理者；
- 通用 Agent 编排器或 AI 决策编辑框架；
- 在协调主张得到验证前，就成为聊天、Git、CI、测试或现有项目管理系统的直接替代品；
- 适用于所有产品阶段的强制软件工程流程；
- 在缺少可评审证据时自动推断 Product Capability 真相的系统。

这些是当前证据路线的边界，并不否定长期的平台目标。
