# Intero 产品路线图

[English](PRODUCT_ROADMAP.md) · 简体中文

## 目的

Intero 不预先承诺一套普适的 AI 原生软件工程方法。团队结构、协调成本和有效流程，可能在探索、快速交付、稳定化和维护阶段表现得完全不同。这些差异本身就是需要研究的问题，而不是产品可以暗中预设的答案。

因此，路线图以证据门槛推进，而不是以功能数量或固定日历推进。每个阶段都必须先证明一个范围更窄的判断，Intero 才扩大产品界面或 Agent 权限。

## 产品主张

Intero 是面向软件团队的协作感知层。在这样的团队中，人与 Coding Agent 正在以越来越高的自主性工作：

> 在不监控私人活动、不把每一个 Agent 动作都变成打扰的前提下，帮助团队及时发现哪些独立工作需要共同理解、协调或重新验证。

这个主张可以跨越不同工作阶段。阶段之间变化的是信号、风险阈值和所需证据，而不是团队维持可信共享现实的需要。

## 产品结构

### 核心产品

以下能力必须成为可信而连贯的整体：

- 有隐私边界的 Agent Work State 和明确共享的 Claims；
- 作为环境感知而非任务排序的 Team Pulse；
- 可解释的冲突、依赖和相关性检测；
- 边界明确的 Coordination Thread；
- 只承载具体人类决策与承诺的 Action Inbox；
- 来源、授权、纠正、去重和恢复机制。

### 兼容上下文

Project、Epic、Feature、Work Item、Sprint、Spec Review、代码引用和未来的外部系统集成，可以帮助 Intero 理解已经声明的工作。它们是有用的上下文，但不是产品主张，也不应要求 Intero 拥有团队的每一个权威系统。

### 研究支线

以下方向仍然是可以被证伪的假设：

- 发现 Agent 没有明确声明的语义关系；
- 随工作阶段或风险变化的协调阈值；
- Product Capability 重建和 Capability Health；
- 更广泛的 AI 原生团队软件工程模型。

只读研究可以并行进行。但在达到各自的证据门槛之前，这些方向不应获得新的领域对象、数据库迁移、自动修改能力或顶级产品页面。

## 交互模型

Intero 应该逐级使用人的注意力：

```text
环境感知
→ 上下文相关性
→ 明确的人类行动
→ 人类确认的后果
```

| 层级           | 产品行为                                                 |
| -------------- | -------------------------------------------------------- |
| 环境感知       | Team Pulse 和静默刷新的摘要；不做日常打扰                |
| 上下文相关性   | 相关人员正在查看上下文时，显示可解释、可忽略的小提示     |
| 明确的人类行动 | 只有决策、评审或承诺才创建一个去重后的 Action Inbox 项   |
| 人类确认的后果 | 需要预览、授权、审计、幂等，并且可以撤销的修改或关闭操作 |

“可能相关”不等于“需要行动”。模型置信度也不等于打扰某个人的权限。

## 以证据推进的路线图

这里的 `R` 代表研究和交付门槛，而不是版本发布日期承诺。

### R0 — 可信的产品基线

在增加新的大型产品界面之前，先完成现有产品闭环工作和目标基础设施上的发布验证。

退出证据：

- Agent、Work State、实时状态、Action Inbox 和授权主链路可恢复、可观测；
- 发布基线保持绿色；
- 在目标环境中完成生产级容量、故障切换和 Canary 验证；
- 隐私或人类权限失败始终是硬阻塞。

### R1 — 证明协调内核

让一组严格对照案例通过真实、经过授权的 Work State：

1. 一个兼容的跨边界修改保持安静；
2. 对同一个共享边界持有不兼容假设时，只创建一个边界明确的 Coordination Thread。

第一版应该优先使用明确、结构化、可共享的边界 Claims，并进行确定性匹配。模型可以解释候选冲突，但不能成为产品宣布冲突的唯一依据。

退出证据：

- 控制案例不创建 Thread、提示或 Inbox 项；
- 冲突案例识别出正确的共享边界、来源和人员；
- 重放不会产生重复 Signal 或 Thread；
- 不暴露原始提示词、文件、Diff、终端输出或私人 Work State；
- 链路来自真实 MCP 和 Worker，而不是预置的 Coordination 数据。

### R2 — 证明低噪音协作

把检测到的冲突变成完整交互：

- 在来源 Room 中显示一个临时讨论入口；
- 在原位置静默更新简短摘要；
- 只在相关人员查看上下文时显示可解释提示；
- 只有确实需要决定或确认时才进入 Action Inbox；
- 在同一个 Room 入口中回显人类确认的结构化结论。

退出证据：

- 摘要刷新不增加消息、未读数或普通通知；
- 被动相关性不创建 Action Inbox 项；
- 相关人员无需额外口头解释即可解决冲突；
- Room、Coordination Thread、Inbox 和相关工作状态之间没有矛盾；
- 纠正、忽略、重试和重放都保持安全。

### R3 — 跨工作阶段试点

先使用研究标签，而不是实现新的“工作模式引擎”，比较：

- 探索；
- 快速交付；
- 稳定化；
- 维护。

观察相关信号、可接受的不确定性和介入阈值，是否会随着可逆性、影响范围、产品成熟度和运行风险而变化。

退出证据：

- 有价值的协调能力在多个真实事件中重复出现；并且
- Intero 要么在不止一个工作阶段证明价值，要么主动收窄到价值真实存在的阶段和团队类型。

### R4 — 只读 Capability Health 实验

收集团队内部真实事件、进行外部问题调研，并从现有授权证据中重建 Product Capability 候选。每个候选都必须允许人接受、纠正、合并、拆分或拒绝。在证明有效之前，健康状态投影保持静默，不能自动创建协调工作。

退出证据：

- Capability Health 提供了 Feature Tracker、Work State、测试或现有项目系统没有表达的信息；
- Capability 粒度和纠正成本可以接受；
- `supported`、`at_risk` 和 `regressed` 都能由当前证据解释；
- 兼容的控制案例保持安静，而矛盾证据只创建一条有效协调路径。

### R5 — 决定产品边界

根据累积证据决定 Intero 应该：

- 主要保留为冲突与注意力协调层；
- 扩展为更广泛的产品共享现实感知层；
- 让 Capability Health 保持只读辅助能力；
- 通过集成获取更多项目管理上下文，而不是自己拥有；
- 收窄到特定类型的 AI 密集型团队；或者
- 停止没有通过验证的假设。

收窄或否定一个方向也是有效结果。

## 衡量方式

Intero 不应该优化摘要、Thread、任务或通知的数量。应该衡量：

- 有效冲突的准确率，以及通过抽样发现的漏检率；
- 每人收到的错误提示和 Inbox 打扰；
- 从冲突状态出现到被发现、确认和关闭的时间；
- 用户是否仍然需要在产品外解释到底发生了什么；
- 是否在集成或发布前发现回归和不兼容修改；
- 人类纠正和忽略 AI 判断的比例；
- 必须为零的隐私、授权和不可逆越权事件。

长期结果是：

> 在保留团队自主性和交付速度的同时，减少团队共享现实悄然分叉的次数。

## 明确不做什么

当前路线图不承诺 Intero 成为：

- 分配和批准所有工作的中央 AI 管理者；
- 通用 Agent 编排器或 AI 决策编辑框架；
- 聊天、Git、CI、测试或项目管理系统的替代品；
- 适用于所有产品阶段的强制软件工程流程；
- 在缺少可评审证据时自动推断 Product Capability 真相的系统。
